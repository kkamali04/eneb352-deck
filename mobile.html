01. The Problem

The Internet Wasn't Built for Distance

When a user in Tokyo requests a website hosted in Virginia, the packet travels approximately 11,000 kilometers through fiber optic cables. At two-thirds the speed of light, that is a 70ms one-way trip, 140ms round-trip.

Add TCP three-way handshake (1 RTT, as covered in our TCP lab), TLS negotiation (1-2 RTTs), server processing, and database queries, and you are looking at 300-500ms before the browser receives the first byte. On mobile 3G networks, this exceeds 1 second.

02. Protocols Involved

A Stack of Protocols

A CDN uses several protocols together to move web content closer to the user. IP Anycast and BGP help choose the nearest edge server, while TCP, UDP, TLS, and HTTP handle the actual connection and data transfer.

At the application layer, DNS resolves names to IPs, HTTP delivers content, and TLS encrypts everything. As we studied in Kurose and Ross Chapter 2, these protocols work together to deliver web content efficiently.

DNS Anycast BGP TCP TLS 1.3 HTTP/1.1 HTTP/2 HTTP/3 (QUIC) 802.11 WiFi IPv4/IPv6
Layer 3-4: Routing & Transport
Anycast IP + BGP route users to the nearest Point of Presence. TCP BBR optimizes throughput.
Layer 5-7: Application
HTTP/3 over QUIC eliminates head-of-line blocking. TLS 1.3 with 0-RTT cuts handshake latency to zero.
03. DNS & Anycast Routing

Finding the Nearest Server

When you type example.com, DNS does not return one IP. CDNs use GeoDNS or Anycast to direct you to the nearest Point of Presence.

Anycast means hundreds of servers share the same IP. BGP routing directs your packet to the closest server based on network topology. If a PoP fails, traffic reroutes automatically.

Cloudflare: hundreds of cities Akamai: 4,400+ edge PoPs

04. HTTP Evolution

HTTP/1 -> HTTP/2 -> HTTP/3

Feature HTTP/1.1 HTTP/2 HTTP/3 (QUIC)
Transport TCP TCP UDP + QUIC
Multiplexing No (6 conn limit) Yes (streams) Yes (independent)
Head-of-line blocking Yes At TCP layer Eliminated
Handshake RTTs 2-3 2-3 0-1
Throughput (ideal) Limited by 6 conn High (single conn) Highest (no HoL)
Connection migration No No Yes

HTTP/3 uses QUIC over UDP instead of TCP. This helps because packet loss on one stream does not block every other stream the same way TCP can. On mobile or lossy networks, that can reduce delay and make page loading feel smoother.

05. TLS 1.3

Zero Round-Trip Time

TLS 1.3 (RFC 8446) reduces the handshake from 2 RTTs to 1 RTT for new connections, and 0-RTT for returning visitors.

On repeat visits, the client sends encrypted data in the very first packet. No handshake needed. For a cached resource at the edge, this means instant delivery.

TLS 1.2: 2 RTT TLS 1.3: 1 RTT TLS 1.3 + 0-RTT: 0 RTT

06. Cache Architecture

The Three-Layer Cache Hierarchy

EDGE
Closest to users. Serves 80-95% of requests. Cache TTL: minutes to hours.
v
REGIONAL
Shared across edge nodes. Handles cache misses. Reduces origin load.
v
ORIGIN
Your actual server. Only hit on true cache misses. Protected by origin shield.

This tiered design, similar to the DNS hierarchy we analyzed in class, means your origin sees only 5-20% of total traffic. The edge absorbs the burst, the regional cache handles spikes, and the origin stays healthy.

07. Cache Control

Cache Headers Control Everything

Cache-Control: max-age
How long the CDN can serve this without checking origin. Static assets: 1 year. HTML: 5-60 min.
s-maxage vs max-age
s-maxage controls CDN caching; max-age controls browser caching. Different values for different layers.
stale-while-revalidate
Serve stale content while fetching fresh in background. Users never wait for revalidation.
# Optimal CDN cache headers
Cache-Control: public,
  max-age=31536000,
  s-maxage=86400,
  stale-while-revalidate=3600

ETag: "abc123"
Last-Modified: Wed, 05 May 2026

# CDN response on cache hit:
cf-cache-status: HIT
# On miss:
cf-cache-status: MISS
08. Cache Invalidation

The Hardest Problem in CS

When you update content, stale versions may linger in CDN caches worldwide until TTL expires.

1. Purge API
Call the CDN API to invalidate specific URLs instantly. Cloudflare propagates purges across all PoPs in approximately 30 seconds.
2. Cache Busting
Add content hash to filenames: app.abc123.js. Instant invalidation, no purge needed.
3. Surrogate Keys
Tag content with keys. Purge by key to invalidate thousands of URLs at once. Fastly pioneered this.
# Cloudflare Purge API
curl -X POST \\
  https://api.cloudflare.com/client/v4/zones/ID/purge_cache \\
  -H "Authorization: Bearer TOKEN" \\
  -d '{"files":["https://example.com/style.css"]}'

# Fastly Surrogate Key Purge
curl -X POST \\
  https://api.fastly.com/service/ID/purge/product-123 \\
  -H "Fastly-Token: TOKEN"

11. Trade-offs: Latency vs Cost

Latency vs Cost vs Complexity

Latency Win
CDNs cut latency from 200ms to 20ms, a 10x improvement. But edge compute adds cost per request.
Cost Trade-off
Origin bandwidth drops 80-95%, but CDN egress fees apply. At scale, multi-CDN optimizes pricing.
Complexity Tax
Cache invalidation, SSL certificate management, and vendor-specific APIs add operational overhead.
Power & Energy
Edge servers consume power 24/7. A global CDN uses megawatts of electricity. However, reduced origin load and shorter transmission distances can lower overall network energy consumption.

12. More Trade-offs

Cache Invalidation Hell

Thundering Herd
When cache expires, thousands of requests simultaneously hit the origin. Solution: origin shield + stale-while-revalidate.
SSL Termination
CDNs decrypt TLS at the edge. However, end-to-end encryption to origin is available (Cloudflare Full Strict, CloudFront Origin SSL). Without it, data travels in plaintext inside the CDN backbone.
Vendor Lock-in
Edge compute is vendor-specific. Migrating means rewriting edge logic. Multi-CDN reduces risk.

The fundamental tension: caching improves performance by increasing staleness. The faster your cache, the longer stale content may persist. Finding the right TTL is an art.

13. Improvement: Edge Compute

Edge Compute: Code at the Edge

I would implement edge compute for dynamic content. Instead of routing every request to origin, run lightweight logic at the edge. Cloudflare Workers (V8 isolates) and Fastly Compute (WebAssembly) both enable this architecture.

A/B testing, personalization, and API aggregation happen 5ms from the user, not 200ms from the origin. This is a fundamental architecture shift.

Workers (JS/WASM) Lambda@Edge Fastly VCL
The Future: Edge-First

Traditional: User -> CDN -> Origin -> Database -> Origin -> CDN -> User

Round-trip: 200-500ms

Edge-First: User -> Edge Worker -> D1/KV -> User

Round-trip: 5-20ms

14. Improvement: HTTP/3

HTTP/3 Adoption is Critical

I would enable HTTP/3 immediately on all CDN properties. As of 2026, approximately 35% of web traffic uses HTTP/3. The holdouts are enterprise firewalls that block UDP and legacy load balancers.

HTTP/3 shines on mobile networks where packet loss is common. On a 3% packet loss connection, HTTP/3 loads pages 2x faster than HTTP/2.

Recommendation
Enable HTTP/3 on your CDN immediately. The protocol is mature, supported by all major browsers, and the gains are free.

15. Improvement: Smarter Caching

Smarter Cache Prediction

ML-Driven Prefetch
Use machine learning to predict what users will request next. Prefetch to edge before they ask. Netflix uses this for thumbnails.
Tiered TTL
Hot content gets short TTL for freshness. Cold content gets long TTL for efficiency. Dynamically adjusted.
Real-time Purge
WebSocket-based invalidation. When origin updates, push purge events to all edge nodes instantly.

The next improvement is smarter caching that can predict likely requests and move content to the edge earlier.
